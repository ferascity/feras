Feras — UI-Only Build Spec

Stack: Expo (React Native) · TypeScript · No backend, no wallet txns, no chain calls — mock data only

0. Scope Contract

In scope Out of scope (this phase)
Every screen, navigation flow, component, animation, loading/empty/error state Real Solana transactions, real wallet signing
Real chessboard rendering + scripted move replay from mock game data Actual agent execution/sandboxing
Bet slip UI, odds UI, confirmation UI Real betting logic, real odds calculation, payouts
Agent submission wizard UI Actually running/scoring a submitted agent
Local/static mock data, fake async delays for realistic loading states Any live API, database, or backend

Rule: every screen must work standalone against a local mock JSON/TS file. No screen may assume a backend exists. This makes swapping mocks for real API calls later a drop-in replacement, not a rewrite — mock functions should mirror the exact shape a real API/RPC call would return.

Chessboard (the centerpiece)

Package Verdict
react-native-chessboard (enzomanuelmangano) Primary pick. Gesture-driven, animated, ref-based programmatic move() API — exactly what you need to replay a mock game move-by-move on a timer. Takes an initial FEN, exposes a ref for scripted moves, has built-in highlight/promotion/checkmate visuals.
rn-chessboard (leomino) Backup option — newer, actively developed, supports full legal-move set + board rotation, but "work in progress" per its own README. Use only if the primary lib blocks you on styling.
chess.js Not a UI lib — a move-generation/FEN engine. In this UI-only phase, use it purely as a mock-data generation helper (offline, in your data script) to produce realistic legal move sequences/FEN strings for replay data, not as runtime game logic in the app.

Rule: the chessboard component never owns "is this a legal move" logic in this phase. It only renders a position and animates a scripted sequence of {from, to} moves pulled from mock JSON, on a timer, to simulate "agents playing live."

3. Design System Rules

  • Dark-first. This is a spectator/betting product used in short bursts, often one-handed — high contrast, large tap targets, legible odds at a glance.
  • One accent color per semantic meaning, fixed across the app: green = favorable odds/win, red = unfavorable/loss, one brand accent for primary CTAs. Never repurpose these for anything else.
  • Numerics get their own type scale (tabular figures) so odds/balances don't jitter as digits change width.
  • Every interactive element has a pressed + disabled state defined up front — bet slip buttons in particular need very explicit disabled styling since "can't bet" is a common real state later (closed market, insufficient mock balance).
  • No screen ships without loading, empty, and error variants, even though errors are simulated. Build all three at the same time as the "happy path," not after.
  • Component library lives in components/ui/ and is the only place raw NativeWind class soup is allowed to accumulate — screens compose primitives, they don't reinvent them.

4. Mock Data & Fake-Async Layer

Every services/api/*.ts function follows this shape so it's indistinguishable from a real API at the call site:

export async function getLiveMatches(): Promise<Match[]> {
  await delay(400 + Math.random() * 400);       // simulate network
  if (shouldSimulateError()) throw new ApiError('...'); // rare, seeded
  return MOCK_MATCHES;
}

Used through React Query (useQuery(['matches','live'], getLiveMatches)), so every screen already has real isLoading / isError / data branches wired — when Phase 2 replaces the function body with a real fetch, zero component code changes.

Rule: mock game replays are pre-scripted, legal chess games (generate with chess.js offline, not at runtime) stored as ordered move lists with timestamps, so ChessBoardReplay can "play" a live match convincingly on a loop or on-demand.

6. Build Phases (UI only)

Phase 0 — Foundation Expo project init (SDK 57, TS, expo-router), NativeWind + theme tokens configured, folder structure scaffolded, Storybook wired, ESLint/Prettier baseline. No screens yet.

Phase 1 — Design System Build every components/ui/ primitive in Storybook first (Button, Card, Tag, Sheet wrapper, Skeleton, Input, Stepper) with all states (default/pressed/disabled/loading). This is the phase that prevents visual drift later.

Phase 2 — Navigation Shell & Static Screens Wire expo-router tab + stack structure. Build every screen with static mock data, no animation yet, no live chessboard — just correct layout, correct data shapes, correct loading/empty/error variants via the fake-async layer. Full breakdown below.

Phase 3 — Chessboard Integration Integrate react-native-chessboard, build ChessBoardReplay driven by scripted mock move data, get move animation, highlight, and check/checkmate visuals working standalone in Storybook before dropping into Match Detail.

Phase 4 — Interactive Layer Bottom sheets (bet slip, agent detail, wallet connect), forms (submission wizard with validation UI only), odds ticker live-updating from a mock interval, haptics + toasts on key actions.

Phase 5 — Motion & Polish Moti/Reanimated micro-interactions (card entrances, live-pulse indicators, odds tick color-flash), Lottie moments (win/submit success), skeletons everywhere a fetch happens, empty states with illustration + CTA.

Phase 6 — QA & Handoff Cross-platform pass (iOS + Android — Solana dApp Store is Android-first, but don't let iOS visibly break), accessibility pass (tap target sizes, contrast, screen-reader labels on the board and odds), and a written map of every mock function in services/api/ → the real endpoint/RPC call it will become, for the next (functional) phase.

6a. Phase 2 — Detailed Breakdown

Exit criteria for this phase: the app is fully navigable end to end, every screen renders real layout against typed mock data through the fake-async service layer, every fetch boundary has a working loading/empty/error variant, and nothing crashes — with zero animation and zero live chessboard (a static board render stands in for it, see 6a.3).

6a.1 Mock data contracts

Define these in types/ first — every mock file and every services/api/* function returns these shapes, so Phase 2's placeholder data and Phase-5-onward's "real" data are structurally identical.

type AgentStyle = 'aggressive' | 'positional' | 'balanced' | 'experimental';

interface Agent {
  id: string;
  name: string;
  avatarUrl: string;
  ownerHandle: string;
  elo: number;
  wins: number; losses: number; draws: number;
  style: AgentStyle;
  isOwnedByUser: boolean;
  createdAt: string;
}

interface Match {
  id: string;
  status: 'live' | 'upcoming' | 'completed';
  agentWhite: Agent; agentBlack: Agent;
  startTime: string;
  fenSnapshot: string;        // current/final position — static preview only in Phase 2
  viewerCount: number;
  oddsWhite: number; oddsBlack: number;   // decimal odds, e.g. 1.85
  winnerAgentId?: string;
}

interface Bet {
  id: string; matchId: string; agentId: string;
  amountMock: number; oddsAtPlacement: number;
  status: 'pending' | 'won' | 'lost';
  placedAt: string;
}

interface LeaderboardEntry {
  rank: number; agent: Agent; winRate: number; totalMatches: number;
}

interface MockWallet { address: string; balanceMock: number; connected: boolean; }

Each gets a matching services/api/*.ts function (getLiveMatches, getMatch(id), getAgents, getAgent(id), getLeaderboard, getBetHistory, submitBet, submitAgent) following the delay/error-simulation pattern from section 4, each consumed via a React Query hook (useLiveMatches, useMatch(id), etc.) in hooks/.

6a.2 Navigation shell

  • app/_layout.tsx — root layout; reads connected from the mock wallet store and redirects to (onboarding) if false, otherwise renders (tabs). This is the only routing "guard" in the app.
  • app/(tabs)/_layout.tsx — tab bar: Home, Arena, My Agents, Activity, Profile. Icons switch fill/weight on focus (Phosphor).
  • Stack screens (match/[id], agent/[id], agent/submit, agent/[id]/sandbox) live outside the tab group so they push full-screen with a back header, per expo-router file conventions.
  • Every stack screen header: back button + screen title only in Phase 2 — no contextual header actions yet (those arrive with interactivity in Phase 4).

6a.4 Definition of done for Phase 2

  • Every route above exists and is reachable via real navigation (no dead links)
  • Every data-bound screen has verified loading, empty, and error renders (trigger the error path manually via the seeded shouldSimulateError)
  • TypeScript has zero any in types/ and services/api/
  • No screen imports from mocks/ directly — only through services/api/
  • Static board renders correctly on both a small (SE-size) and large device width

7. Rules to Follow Throughout

  1. No screen talks to mocks/ directly — always through services/api/.
  2. No real chain/network code in this phase — not even a "just in case" fetch. Keep the surface 100% offline-capable.
  3. Every async boundary shows loading, error, and empty states — never assume happy path.
  4. The chessboard never validates moves — it plays a script. Legality lives in mock-data generation (offline), not runtime.
  5. One design-system primitive per concern — if you're about to write a one-off styled View that looks like a Button, stop and extend the Button primitive instead.
  6. Wallet/agent-execution/betting logic is always behind an interface (IWalletService, etc.), even though only a mock implementation exists right now.
  7. Component code has zero knowledge of "mock" vs "real" — that distinction lives only in services/.
  8. Every submission/bet action needs a disabled + confirmation state, even fake — this is the UX you'll least want to redesign once real stakes are involved.
  9. Build in Storybook before wiring into a screen for any non-trivial component (board, bet slip, submission wizard, odds ticker).

What comes after this phase

Once the UI is complete and reviewed, Phase 2 (functionality) becomes: implement real services/api/* calls, swap MockWalletService for a real MWA-backed implementation, add real agent sandboxing/execution, and — as covered earlier — settle the legal/licensing question before any real-money bet path goes live. None of that requires touching component code if the interfaces above are respected.
